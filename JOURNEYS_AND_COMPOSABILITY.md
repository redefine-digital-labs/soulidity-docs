This is a product and interface specification. Coverage here means that a requirement is represented in the documentation; it is not a passing product test, frozen ABI, deployed capability or third-party adoption. The English publication preserves original journey identifiers without creating a replacement backlog.

## Independent entrances and useful stopping points

| Entrance | Useful result | Optional continuation | Required boundary |
| --- | --- | --- | --- |
| Local editor or imported legitimate project | Reopenable Maker, preview, recipe or output | Publish later with a supported tool | Exact schema/resources and backup; no mandatory chain action |
| Independent Native or compatible producer | One standard Soul with authentic provenance | Management, use or a selected service | Producer's real authority and source policy; no mandatory Maker |
| Existing, received or bought compatible Soul | Open and manage the same asset | Supported runtime, wardrobe or market | Current custody and rights; no reissuance to enter |
| Maker/Pack Player | Permitted composition and saved output | Optional Complete issuance and management | Exact definitions, qualification, fees and three component modes |
| Alternative management/runtime client | Read or act on supported original objects | Replace another compatible client | Public contracts, scoped authority and actual infrastructure |
| Market, channel or community discovery | Complete the selected independent service | Return to management or another service | Service-specific instance and obligations; no compulsory ecosystem funnel |

Every boundary preserves identity and effective rights while permitting pause and continuation. Replacing a client does not migrate a service instance or transfer its ledger. An incompatible historical asset needs explicit supported handling or migration, not a counterfeit new identity.

## Module boundaries

A module is a responsibility and authority boundary. A repository, Move package, SDK artifact and product are different units; one repository can contain multiple packages, and a shared package can imply shared upgrade control. The following are logical targets, not a claim that every release is available.

| Module | Owns | Dependency and authority boundary |
| --- | --- | --- |
| STANDARD | Minimal identity, provenance and safe-root contract | No reverse dependency on Maker, Market, Channel, Community or a global business Config. |
| CONTENT | Content references, lifecycle, access and recovery | Generic content can stand alone; select a Soul adapter when required. No transfer/spending authority. |
| MAKER | Definitions, releases, Packs, qualifications, supply and issuance adapters | Maker core can stand alone; Soul production uses a declared adapter. One authoritative supply/qualification state. |
| CHANNEL | Scoped distribution agreements, terms, quotas and service income | No compulsory Market, no asset-wide control and no second supply ledger. |
| MARKET | Orders, custody, quotes, cancellation, delivery and settlement | No compulsory Channel; asset-maintained adapters enforce actual asset obligations. |
| EXTENSIONS | Selected visual, component, history and other capabilities | Independent namespace, state and scoped writes; mandatory effects require consumer support. |
| COMMUNITY | Profiles, posts, comments, relationships and pagination | No authority to create assets, issue qualifications or control transfers. |
| SDK | Nine optional read/build/adapter capability groups | No business authority, custody or universal all-module dependency. |
| DEVOPS | Pinned build, release and operating tools | No mandatory business runtime dependency or ecosystem signer. |
| INTEGRATION | Exact-version combinations and interoperability evidence | No protocol registration authority, asset admission or central business state. |

The SDK capability groups are standard reads, root operations, Maker publication, issuance, content, community, market, channel and extension adapters. Consumers import only selected functionality. Optional protocol integrations do not become mandatory dependencies through the SDK.

### Required module release manifest

A consumable release records: owning source and revision; package/artifact IDs and digests; exact public schemas and type origins; provided and consumed interface families; supported networks and service instances; compile/runtime/behavior/authority/funds/state/content dependencies; capability effects; normal and error results; custody and authorization assumptions; cancellation, recovery and migration; upgrade authority; code/content licensing; and verification evidence. References to a floating “latest” cannot establish a tested version pair.

The API and examples expose the minimum required inputs. Consumers must not depend on private witnesses, unrestricted root mutation, an internal admin endpoint, another module's mutable ledger, or undeclared configuration. Adapter-owned asset rules remain authoritative; capability descriptions and historical receipts are not reusable authorization.

### Examples of dependency direction

An editor may stop at a file. Maker publication can stop at a release. Issuance connects a chosen producer to Standard. Standard does not import the producer. A market can settle an asset through its supported adapter without importing that asset's game. A game can recognize a Soul without using a market. Community and discovery can reference these products without becoming creation permission. Generic Content need not import Soul unless a chosen adapter uses it.

These are separate kinds of combination: file/format exchange, content retrieval, capability discovery, authorized state mutation and atomic financial settlement. Passing one does not establish the others. Runtime composition also does not imply that every package can compile without any shared core dependency.

## Compatibility and takeover acceptance

1. Freeze a coherent source, dependency lock, configuration and artifact baseline. Historical production, an evolving new target and a frozen acceptance target are different baselines; do not demand that an unrelated historical market accept new types without an explicit migration.
2. Test baseline/current, candidate/current and candidate/candidate combinations. Add reverse combinations where actual dependencies require them. Pin network, type origin, schema, custody path, service instance and content manifest.
3. Add an independently maintained passive appearance or history namespace. The original Soul must still list, cancel and settle against the frozen market; its source, lock, configuration and artifact remain unchanged, with zero forced market releases.
4. Verify each capability's read/write/carry/handover behavior and its funds, authority, supply, transfer, content and exit/history effects. Ignore only unsupported optional presentation; reject unknown mandatory obligations and incorrect proof or generation.
5. Use an independent producer and alternative client on the same supported asset. Disconnect platform-specific services and prove the declared operations remain possible using available public infrastructure and content. Distinguish client replacement from migration of orders, grants, balances or quotas.
6. Exercise normal operation, wrong identity/root/instance, revoked/expired permissions, insufficient funds, concurrent final supply, changed composition, cancellation, uncertain results and cold recovery. Unknown results query the same attempt; current read failure does not erase past success.
7. Separate evidence states: designed, implemented, locally tested, independently accepted, canonical source cutover, released, deployed and externally adopted. A passing internal sample cannot close full-product or independent-adoption acceptance.

### Authorization, continuity and exit invariants

- Each supply/counting dimension and each service ledger has one actual authority. Changing a client, channel or product controller does not duplicate or reset it.
- Business payment, entitlement, supply and final delivery share their required atomic boundary. Multi-system upload/publication retains persistent checkpoints and exact successful resources.
- Controlled handover rotates supported grants; freely transferable paths cannot rely on an automatic hook to revoke unsafe detached authority. A transfer away and back does not silently revive a grant.
- New service instances do not inherit balances, orders, quotas, capabilities or access policies. Explicit migration protects legitimate outstanding obligations and exits.
- Physical consume and voucher redemption use real supply and replay checks; a chain receipt is not proof of external shipment. Collection membership, display grouping and transferable rights are distinct.
- Public availability does not grant commercial/artwork permissions, and a wallet holding an asset does not establish all copyright. Code licenses, content licenses and service terms are separately disclosed.
- Wallet keys, seed phrases, keystores, tokens and browser credentials are excluded. Signed recovery payloads and private drafts still require confidentiality and controlled access.

## Delivery and completion

Start with direct creation or receipt, management, one real supported use and cold continuation. Complete each independent Maker, composition, commerce, content, Physical, community and application branch under its retained policies. Do not turn this sequence into a mandatory user funnel or use the core loop to remove other required scope.

Each increment follows Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → Plan in the original GitHub/Slack records. Review requirements are based on the actual money, authority and safety impact. Exact deployment smoke checks and operations/reconciliation follow a released candidate. Current unfinished evidence remains in the [implementation status](IMPLEMENTATION_STATUS_20261017.md).
